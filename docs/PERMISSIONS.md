# Permissions, agents and roles

Status: accepted 2026-10-26. The default config that implements this lives in
[examples/broker.yaml](../examples/broker.yaml).

## Model in one paragraph

One broker runs per host (hosted by the tray app) and listens for MCP over Streamable HTTP.
Every connection is resolved to an **agent** (who is calling), each agent has one **role**
(what it may see and do), and every tool call is classified into a **class** (what kind of
effect it has). The role maps classes to `allow`, `approve` or `deny`. Global **floors** can
only make a decision stricter, never looser. A small set of **hard guards** is built in and
cannot be configured away.

```
request ─▶ network gate ─▶ identify agent ─▶ role grants connector? ─▶ classify tool
        ─▶ role rules / class default ─▶ max(strictness, global floors, hard guards) ─▶ decision
```

Strictness order: `allow` < `approve` < `deny`.

## 1. Network gate

- The broker listens on `0.0.0.0:8765` (MCP at `/mcp`, dashboard at `/ui`).
- `server.allowed_sources` is a CIDR allowlist checked before anything else. The default
  covers loopback, RFC 1918 private ranges, the Tailscale CGNAT range and IPv6 ULA/link-local.
  Anything else gets a TCP-level reject and an audit entry.
- Any connection from a non-loopback address must present a valid agent token. There is no
  anonymous LAN access.
- The tray app creates the Windows Firewall inbound rule for the **Private** network profile
  only, so the port is closed when the laptop is on a Public network (café, hotel).
- TLS is optional (`server.tls`). Without it, tokens cross the LAN in clear text, which is
  acceptable on a trusted home network but worth knowing.

## 2. Agent identification

Each agent has a name, a role and its own token. The token decides which agent a connection is.
The agent's `match` conditions are extra constraints that must also hold. If they don't (say,
the VS Code token is used by a process that isn't `Code.exe`, or from a LAN address), the
request gets 403 and an audit entry. So a leaked token is only useful from where the agent
really runs.

| Signal | Strength | Where it works |
|---|---|---|
| **Token** (`Authorization: Bearer mcpb_...`) | Strong. The primary identity. | Everywhere |
| **Process** (`match.process`) | Strong when combined with a token. The broker maps a loopback TCP connection to its PID, then walks the parent chain and matches executable paths. | Windows host only (loopback) |
| **Source network** (`match.from`) | Restricts where a token may be used from. | Everywhere |
| `clientInfo.name` from MCP `initialize` | None. Self-reported, trivially spoofed. | Logged in the audit only |

Tokens:

- Generated by the tray app (`mcpb_<agent>_<32 random bytes base64url>`), shown once, and
  stored only as SHA-256 hashes in `tokens.yaml` (0600, next to `broker.yaml`). `broker.yaml`
  itself contains no secrets, so it can be shared or committed.
- The stdio shim (`mcp-broker connect --agent vscode`) reads its token from the user config dir,
  so client configs like `claude_desktop_config.json` never contain a token. From WSL the shim
  reads `MCP_BROKER_TOKEN` or `~/.config/mcp-broker/token`.
- Rotation and revocation happen from the tray; revocation takes effect on the next request and
  closes open sessions for that agent.

A process match passes if any process in the caller's parent chain matches. Claude Code
running inside VS Code has both `claude.exe` and `Code.exe` in its chain, so it passes either
check. Which role it gets depends on which agent's token its shim is configured with.

Connections that match no agent:

- from loopback without a token: role `anonymous` (sees no connectors);
- from anywhere else: rejected with 401.

## 3. Roles

A role answers three questions:

1. **Which connectors can this agent see?** `connectors:` is a list of names, globs or tags
   (`tag:office`), with `!` to exclude. Connectors not granted are invisible. They don't
   appear in `list_connectors`, and `load_connector` reports them as unknown, not as forbidden.
2. **What does each class of tool do?** `classes:` maps each class to an action. Missing
   classes default to `deny`.
3. **What may it do with profiles?** `profiles:` maps `status`, `logs`, `plan`, `start`, `stop`,
   `update` to actions. Missing actions default to `deny`.

Optional `rules:` (first match wins, glob on `<connector>/<tool>`) override the class default
for specific tools *within the role*. Tools that resolve to `deny` are also removed from the
tool list `load_connector` returns, which saves context and avoids tempting the model.

### Default roles

| Role | Intended for | Connectors | read | write | destructive | external | spend | exec | Profiles |
|---|---|---|---|---|---|---|---|---|---|
| `owner` | Claude Desktop, Claude Code on the host | all | allow | allow | approve | approve | approve | approve | start/update approve, rest allow |
| `coder` | VS Code agents on the host | office, browser, media | allow | allow | approve | deny | deny | approve | start approve, stop/status/logs allow, update deny |
| `sandbox` | WSL distros, wslc containers | office, media | allow | approve | approve | deny | deny | deny | status/logs only |
| `viewer` | Phone, other LAN machines | all except mail | allow | deny | deny | deny | deny | deny | status/logs only |
| `anonymous` | Unidentified loopback | none | – | – | – | – | – | – | none |

Mail (`imap`, `sieve`) is `owner`-only by default: it holds credentials, can send as you, and a
Sieve change silently reroutes all incoming mail.

## 4. Tool classes

| Class | Meaning | Name verbs (fallback heuristic) |
|---|---|---|
| `read` | No side effects | get, list, read, search, find, query, status, info, describe, show, inspect, check, validate, verify, count, stats, diagnose, discover, which, capture, snapshot status |
| `write` | Changes local state, reversible or contained | everything not matched elsewhere (unknown verbs land here) |
| `destructive` | Deletes or overwrites, hard to undo | delete, remove, clear, trash, purge, drop, destroy, wipe, reset, reject, truncate, kill, close, bulk |
| `external` | Leaves the machine or acts as you to others | send, forward, reply, share, publish, post, push, upload |
| `spend` | Costs money or paid credits | none (configured per connector only) |
| `exec` | Runs arbitrary or third-party code | install, uninstall, exec, execute, eval, shell, spawn, launch |

Classification, in order:

1. `connectors.<name>.tool_classes` in config. Authoritative because the user wrote it.
2. Otherwise the **strictest** of the name heuristic and the downstream MCP tool annotations
   (`destructiveHint: true` → at least `destructive`). Annotations can only raise the class:
   a downstream server claiming `readOnlyHint` cannot lower a tool named `delete_*` to `read`.

Strictness for picking "strictest": `read` < `write` < `destructive` < `external` < `spend` < `exec`.

## 5. Global floors

`policy.floors` are rules that apply to every agent, and that can only tighten the role's
decision (`final = max(role decision, matching floor)`). Use them for invariants such as
"activating a Sieve script always needs approval, whoever asks".

## 6. Hard guards (built in, not configurable)

- Agents can never change broker config, agents, roles or tokens through MCP. Adding a
  connector means "run this command", so it is only possible from the tray or the dashboard
  admin pages.
- Dashboard admin pages (config, agents, tokens) are only reachable from loopback with the
  admin token. Approvals and run status are reachable from `allowed_sources`, so the phone works.
- Starting a profile with `network_exposed` (or a non-loopback `--listen`) → at least `approve`.
- `kill_foreign` (stopping a process the broker did not start) → at least `approve`.
- Secret redaction everywhere (env values, tokens, `headers` of HTTP connectors). HTTP
  connector header values are always treated as secret, whatever their name.
- Every decision is audited, including denials and invisible-connector probes.

## 7. Approval channels and trust

Approval only means something if a human answers it. MCP elicitation is answered by the
*client*, and a headless agent in a container could auto-accept its own prompt. So each agent
lists the channels its approvals may use:

| Channel | Who answers |
|---|---|
| `elicitation` | The calling client's UI. Only trusted for interactive host apps. |
| `tray` | Windows toast from the tray app with Approve / Deny |
| `dashboard` | `/ui/approvals`, including from the phone |
| `ntfy` | Push notification linking to the dashboard |

Defaults: `owner` agents use `[elicitation, tray, dashboard]`. Every other agent uses
`[tray, dashboard]`, so a WSL or container agent can never approve itself.

The first decision wins, the timeout (default 120 s) denies, and an approval covers that one
call only (no "approve for session" in v0.1).

## 8. Shared connectors and sessions

By default, one downstream process per connector is shared by all agents (`instance: shared`).
The broker keeps per-agent request routing, so elicitations, progress notifications and
cancellations go back to the agent that made the call. Connectors that hold per-user state can
set `instance: per_agent`.
